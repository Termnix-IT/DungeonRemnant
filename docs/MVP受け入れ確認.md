# MVP受け入れ確認

## 1. 文書の目的

この文書は、リアルタイム化したDungeon RemnantのMVP完成条件12項目（[リアルタイム化_再設計計画.md](リアルタイム化_再設計計画.md) の7章）と、実装・自動テスト・手動確認の結果を対応付けるためのものです。ゲームの仕様は [MVP_SPEC.md](MVP_SPEC.md) にあります。

機能が動くことの確認と、遊んだときの面白さ・分かりやすさの評価は分けて扱います。前者は本書の受け入れ確認、後者は末尾の「プレイ時に気になった点・改良課題」に記録します。

ターン制だった旧ゲームのMVP（完成条件22項目）は2026-09に受け入れ済みでしたが、ゲームの作り替えで対象のコードがなくなったため、その判定は本書から外しました。

## 2. 判定

**MVP：手動確認待ち**

12項目のうち、自動テストで確かめられる部分はすべて通っています。操作の手応え、1ランの長さ、ゲームパッドでの通しプレイなど、手で遊んで確かめる部分は、ユーザーの操作確認がまだです。6章のチェックリストを通した時点で判定を更新します。

## 5. 検証実績

### 自動テスト

`rogue-like-play/` で `python tools/run_tests.py` を実行すると、`tests/test_*.gd` の19スイートをすべて実行します。Phase 5の完了時点（2026-10-21）で19スイートすべてが成功しています。

`test_enemy_director` は成功しますが、終了時にGodotが「ObjectDB instances were leaked」の警告を出します。Phase 4の時点から出ている警告で、テストの判定には影響しません。

### 撮影による確認

描画できる環境で次の撮影用Scriptを実行し、画像を目で確かめています。画像は `.godot/` に出ます。

| Script | 確かめる内容 |
| --- | --- |
| `tests/capture_hub.gd` | 拠点のロビー・強化・図鑑・設定を1600×900・1280×720・1920×1080で。ラン中のメニュー、結果画面、帰還後のロビー |
| `tests/capture_run_flow.gd` | 分岐マップ、フィールドとアリーナ、報酬の選択 |
| `tests/capture_boss.gd` | ボスの登場、攻撃の予兆、第2フェーズ |
| `tests/capture_action_sandbox.gd`・`tests/capture_crowd_perf.gd` | sandboxの戦闘と、敵の数ごとのフレーム時間 |

## 6. 手動プレイ受け入れチェックリスト

ゲームを通常起動（F5）して確かめます。

### 操作と手応え

- [ ] 移動の重さと止まり方が気持ちよい。
- [ ] ダッシュの距離と無敵が分かりやすく、敵の攻撃を抜けられる。
- [ ] 攻撃が当たった手応え（ヒットストップの長さ、のけぞり、数字）がある。
- [ ] 3段コンボのつながりと、溜め攻撃の溜め時間がちょうどよい。
- [ ] マウスの方向へ正確に攻撃が向く。
- [ ] ゲームパッドだけで、拠点からランの終わりまで遊べる。

### 戦闘

- [ ] 敵に囲まれても、ダッシュと攻撃で抜け出せる。
- [ ] 精鋭とボスの予兆を見てから避けられる。
- [ ] 敵が多いときにカクつかない。
- [ ] 強化を取ったときに、攻撃の見た目と挙動が変わったと分かる。

### ランと拠点

- [ ] 分岐マップのカードから、選ぶ理由（形式・難易度・報酬）が読み取れる。
- [ ] フィールドとアリーナで遊び心地が違う。
- [ ] 1ランが約10分で終わる。
- [ ] 負けても、残響と永続強化で次のランへ進む動機が感じられる。
- [ ] 戦闘中のメニューから中断すると、結果を経て拠点へ戻り、残響が残っている。
- [ ] 旧ゲームのセーブがある環境で起動すると、残響が換算されて引き継がれ、`progress.json.v4` が残っている。

## 7. 仕様上の意図的な対象外

次の要素はMVPの完成条件に含めず、MVP後の候補とします。

- 探索・イベントフィールド
- 必殺技と2つ目のアクティブスキル
- 武器種の解放
- 遠距離攻撃の特殊敵
- アイテムと装備
- 2つ目以降の章
- 主人公のダッシュ・溜め・被弾の専用アニメーションと、HUDの作り込み（Phase 6で行う）

## 8. プレイ時に気になった点・改良課題

### 記録ルール

1. まず観察した事実を「気になった点」に記載する。
2. 再現条件、期待した状態、実際の状態を分ける。
3. 原因や解決策を決めつけず、プレイヤーへの影響を記録する。
4. 同じ問題を再現または複数回確認してから、改良課題へ移す。
5. 改良課題ごとに優先度と完了条件を決め、Plan承認後に実装する。

優先度は次の基準を使います。

| 優先度 | 基準 |
| --- | --- |
| P0 | 進行不能、データ消失、クラッシュなど、プレイ継続を妨げる |
| P1 | 主要操作・戦闘・ランの流れを大きく損なう |
| P2 | 分かりにくさ、バランス、反復的な不便など、体験を継続的に損なう |
| P3 | 軽微な表示、演出、将来的な拡張候補 |

### 気になった点

| ID | 日付 | 状況 | 気になった点 | 再現手順 | 期待した状態 | 実際の状態 | 影響 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| OBS-006 | 2026-09-12 | GitHub・Windows配布 | プロジェクト固有のアイコンがない | リポジトリまたはWindows版のアイコンを確認する | Dungeon Remnant固有の外観で識別できる | Godot Engineの既定アイコンを使用している | 作品の識別性が低く、Godot公式作品との誤認を招く可能性がある |

旧ゲームの武器の使い分けと1フロアの戦闘量についての観察（OBS-003〜005）と改良課題（IMP-003・IMP-004）は、対象の武器とフロアがなくなったため削除しました。

## 9. 次の進め方

1. 通常起動で1回以上プレイし、6章のチェックリストを確かめる。
2. 気になった点を、重要度を判断せず観察として記録する。
3. 進行不能やデータ消失はP0として先に扱う。
4. それ以外は一度まとめ、重複と原因を整理する。
5. 改良課題に変換し、優先順位を決める。
6. 各課題はPlanを確認してから実装する。
