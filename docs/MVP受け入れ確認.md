# MVP受け入れ確認

## 1. 文書の目的

この文書は、`MVP_SPEC.md`の「42. MVP完成条件」にある22項目と、Phase 1～9で実装・検証した内容を対応付けるためのものです。

機能が動くことの確認と、遊んだときの面白さ・分かりやすさの評価は分けて扱います。前者は本書の受け入れ確認、後者は末尾の「プレイ時に気になった点・改良課題」に記録します。

## 2. 判定

**MVPゲームループ：受け入れ可能**

仕様の完成条件22項目は、実装、自動テスト、Phaseごとの目視確認によって一連の流れとして成立しています。Phase 1～9の目視確認はすべて完了しています。

ただし、これは操作感や難易度を含む最終品質の確定ではありません。今後の実プレイで見つかった問題は、MVPの完成判定を曖昧に戻さず、個別の改良課題として管理します。

## 6. 手動プレイ受け入れチェックリスト

自動テストでは測れない品質を、通常のプレイとして確認します。問題があった項目は、次節の改良課題へ転記します。

### 操作と理解

- [x] 初見でも移動、攻撃方向選択、確定、キャンセルを理解できる
- [x] Inventoryの装備先・取り外し・アイテム使用が迷わず行える
- [ ] 拠点の倉庫で預け入れ・取り出し・Escによる終了が迷わず行える
- [x] ターンを消費する操作と消費しない操作の違いが伝わる
- [x] 安全な既探索区間では長押し移動が機能し、敵・未探索・アイテム・分岐・階段の前後で意図どおり停止する
- [x] 敵3種類の感知・攻撃特性を挙動から判別できる
- [x] 死亡・中断時の損失と装備保護をリザルトから理解できる
- [x] 保存済み／保存失敗／バックアップ復元の表示を理解できる

### 探索と戦闘

- [ ] Room、Cave、OpenAreaで探索体験に違いを感じる
- [ ] Fog of Warが探索を妨げすぎず、先を確認する楽しさにつながる
- [ ] Sword、Spear、Hammerを状況に応じて使い分ける理由がある
- [ ] 敵の数、初期安全距離、アイテム量が極端ではない
- [ ] 1フロアの広さと10Fまでの所要時間が許容範囲に収まる
- [ ] レベルアップ候補が判断を生み、選択頻度が多すぎない
- [ ] 回復薬、装備、敵報酬の量が攻略判断につながる
- [ ] BossのHP・攻撃力・感知範囲が、それまでの成長に対して妥当

### 冒険サイクル

- [ ] 死亡時の50%損失が重すぎず軽すぎない
- [ ] クリア時に全所持品を持ち帰れる価値を感じる
- [ ] 永久HP強化の価格と効果が次の挑戦動機になる
- [ ] 冒険終了からHub、購入、次の冒険開始まで流れが途切れない
- [ ] アプリ再起動後にGold、Inventory、倉庫、装備、永久強化が期待どおり復元される

## 7. 仕様上の意図的な対象外・簡略化

以下は現状の不具合ではなく、MVPの範囲を守るために実装を見送った、または最小化した項目です。実プレイで必要性が確認できた場合にだけ改良候補へ移します。

- Hardモード、高度な敵AI、Hearing、Shared Alert
- 拠点での装備変更、ショップ、修理、帰還アイテム
- 設定画面、図鑑、クイックスロット
- 通常敵5種類・消耗品5種類という仕様上のコンテンツ量目安への到達
- 斧、大剣、短剣、弓、杖など将来武器
- 冒険途中のセーブ・再開
- セーブデータ移行、複数セーブスロット、クラウド同期
- 本格的なアート、アニメーション、サウンド

現在のコンテンツは、通常敵3種類、Boss1種類、武器3種類、防具2種類、Accessory3種類、消耗品1種類、Ability10種類です。設定値はResourceで調整可能です。

## 8. プレイ時に気になった点・改良課題

### 記録ルール

1. まず観察した事実を「気になった点」に記載する。
2. 再現条件、期待した状態、実際の状態を分ける。
3. 原因や解決策を決めつけず、プレイヤーへの影響を記録する。
4. 同じ問題を再現または複数回確認してから、改良課題へ移す。
5. 改良課題ごとに優先度と完了条件を決め、Plan承認後に実装する。

優先度は次の基準を使います。

| 優先度 | 基準                              |
| --- | ------------------------------- |
| P0  | 進行不能、データ消失、クラッシュなど、プレイ継続を妨げる    |
| P1  | 主要操作・戦闘・冒険サイクルを大きく損なう           |
| P2  | 分かりにくさ、バランス、反復的な不便など、体験を継続的に損なう |
| P3  | 軽微な表示、演出、将来的な拡張候補               |

### 気になった点

| ID      | 日付         | 状況・階層       | 気になった点             | 再現手順                                | 期待した状態           | 実際の状態              | 影響                     |
| ------- | ---------- | ----------- | ------------------ | ----------------------------------- | ---------------- | ------------------ | ---------------------- |
| OBS-003 | 2026-09-10 | 武器選択 | 槍の射程が強く他武器を使う理由がない | 槍と剣・ハンマーを比較して進行する | 武器ごとに有効な状況がある | 槍が同威力かつ長射程で優位 | 武器切替と選択の判断が生まれない |
| OBS-004 | 2026-09-10 | 敵との連戦 | 敵配置量が過大 | 1フロアで複数の敵と連戦する | 位置取りを考えながら無理なく探索を続けられる | 戦闘量が多い | 探索より戦闘の比重が大きくなる |
| OBS-005 | 2026-09-10 | 槍ナーフ後の成長 | ダメージ低下後も射程強化が強く、弱体化より他武器強化が望ましい | 槍射程強化を取得して武器を比較する | 各武器の長所を伸ばして選択できる | 槍の成長上の優位が残る | 数値ナーフでは使い分けが成立しない |

## 9. 次の進め方

1. 通常起動で1回以上プレイする。
2. 気になった点を、重要度を判断せず観察として記録する。
3. 進行不能やデータ消失はP0として先に扱う。
4. それ以外は一度まとめ、重複と原因を整理する。
5. 改良課題に変換し、優先順位を決める。
6. 各課題はPlanを確認してから実装する。

この運用により、MVP完成後の追加作業を、根拠のある改良に限定します。
